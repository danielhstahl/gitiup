# ADR-0004 policy vectors (`gitiup-policy-1`)

The golden vectors for [ADR-0004](../0004-published-policy-format-signing-and-resolution.md):
the equivalent, for a published repository policy, of
[`change-v1/`](../change-v1/) for
[ADR-0003](../0003-change-record-format-and-merge-semantics.md) and of
[`selection-v1/`](../selection-v1/) for
[ADR-0002](../0002-roster-verifier-selection-and-sybil-resistance.md). A Rust
`PolicyDocument` that cannot reproduce these files is wrong, however reasonable it
looks — four tickets (`giti-91m.2`, `.3`, `.4`, `.5`) and one quorum ticket
(`giti-zp1.2`) otherwise invent four "published policies" that all claim to be the
one the owner signed.

| file | what it is |
|------|------------|
| `generate.py` | the reference implementation *and* the generator: stdlib-only Python, no clock, no network, its own RFC 8032 Ed25519, and the canonicaliser, PAE framing and fixture keys **imported from `../change-v1/generate.py`** rather than copied (ADR-0003 D11: one canonicaliser) |
| `cases.json` | the index: per policy the `revision`, `signed_by`, `body_digest`, `record_digest`, `kv/` key and ref, the publish warnings, plus the history walk, the publish-time normalisations and the whole refusal table |
| `policies/<case>.json` | the policy bytes **exactly**: Gitiup Canonical JSON (ADR-0001 D1), no whitespace, no trailing newline, signed in place |

| case | what it teaches |
|------|-----------------|
| `personal` | the smallest useful policy: `local` from one named runner key, amd64, 24 h. Note the owner who signs the *rules* is not the key that signs the *proofs*, and nothing requires them to be (`D3`) |
| `project` | the tier is data: `allowed_tiers: ["quorum"]` plus `quorum` = `SelectionPolicy` verbatim (5 seats, 4 agree), and `quorum.requirements` is what a verifier must be able to do (`D5`) |
| `project-tightened` | revision 2, `previous_digest` names revision 1: a policy change is a new signed document, never an edit. The bar moved from 4-of-5 to 5-of-7 and the freshness window halved (`D6`) |
| `fork-inherited` | a fork that changes nothing: **byte-identical**, same body and record digest as `project`. A fork cannot weaken a policy it cannot re-sign convincingly (`D1`) |
| `fork-weakened` | a fork that re-signs a weaker policy with its own key: well-formed, correctly signed, and **refused** by a verifier whose trust roots are upstream's — exit 6, `signer_untrusted`. Refused, not distrusted-and-used (`D3`) |

The clock is fixed (`cases.json:clock_us`), because D6 refuses a policy dated more
than the clock-skew allowance into the future and a regeneration must not depend on
when it ran.

## The refusal table

`cases.json:refusals` is 32 named refusals with the token and the exit code each one
must produce, generated by mutating a real vector and then **re-signing** it — a
defect applied after signing is only a broken signature, and the table would
otherwise teach "bad signature" thirty times. The three cases that *are* only defects
after the fact (a body edited afterwards, a typed `key_id`, an owner that does not
match the signer) are applied afterwards on purpose.

| exit | tokens |
|------|--------|
| 6 | `arch_conflict` `chain_broken` `empty_tiers` `env_match_off` `expired` `expires_before_effective` `field_unknown` `future_dated` `min_signatures_zero` `no_trust_anchors` `not_normalised` `owner_mismatch` `protects_out_of_scope` `required_agree_unreachable` `required_agree_zero` `requirements_unsatisfiable` `revision_gap` `sandbox_disjoint` `sandbox_floor` `sandbox_forbidden` `signature_count` `signer_untrusted` `size_exceeded` `tier_floor_unknown` `tier_not_allowed` `tier_unknown` `unknown_schema` `unsigned` |
| 7 | `bad_signature` `key_id_derivation` (a key id is derived, never typed) |
| 8 | `not_canonical` |

32 rows, 31 distinct tokens: `requirements_unsatisfiable` is reached by two different
defects (an empty sandbox set, a zero resource floor). `digest_mismatch` — also exit 8,
and in `TOKEN_EXIT` — is not in the table because it is not a property of a document: it
is the index check in `--verify`, a stored object whose bytes are not the bytes
`kv/policy/<hex>` promises.

Two refusals cannot be mutations of a document, and are checked directly: an encoding
that is not its own canonical form (`not_canonical`, 8) and a document too big to
encode (`size_exceeded`, 6 — the shared canonicaliser bounds every gitiup record the
same way).

## The history walk, and the normalisations

`cases.json:history` fixes what "the policy in force when the run happened" means for
the `project` chain: a run on 2026-10-07 is judged by revision 1 (4 of 5), a run on
2026-10-25 by revision 2 (5 of 7), and a run before revision 1 took effect is
**refused** (`policy_history_missing`) rather than judged by rules that did not exist
yet (D6).

`cases.json:normalisations` fixes what `gitiup policy publish` does to a tree file
before signing it: `allow_simulated` is resolved into `allowed_tiers`, and lists are
sorted and deduplicated, so two authors who wrote the same rules in a different order
publish **byte-identical** bytes and a re-publish that changed nothing cannot move the
digest a verdict cites (D2, D6).

```console
$ python3 generate.py            # print the table, rewrite the vectors
$ python3 generate.py --check    # fail (exit 1) if the committed vectors are stale
$ python3 generate.py --selftest # primitives, every refusal, the history walk
$ python3 generate.py --verify   # re-derive every committed record from its own bytes
```

## Reproduced in Rust

Yes — `crates/gitiup-quorum/tests/policy_vectors.rs` reads `policies/*.json` and
`cases.json` and proves from **those bytes alone** (never from a Rust constant) that:

* the three fixture identities in `cases.json:keys` derive the key ids the vectors
  name, from `gitiup ADR-0003 change-v1 fixture key: ` + a label exactly as
  [`change-v1/generate.py`](../change-v1/generate.py) derives them;
* `gitiup_attest::canon` re-encodes every committed vector to itself, so the file and
  its digest are one fact and not two that have to be kept in step;
* a signature verifies over the PAE bytes for `application/vnd.gitiup.policy+json` —
  and the same signature is rejected over the payload type of any other record type;
* `body_digest` is the digest of the document with `signatures` removed (so it is
  computable before anyone signs, which is what `gitiup policy publish --dry-run`
  prints) and `record_digest` is the digest of the stored bytes, which is the
  `kv/policy/` key — both re-derived here and compared with `cases.json`;
* the validator reaches the same token and exit code for all 32 rows of
  `cases.json:refusals`, which is the point of the table: `.2`, `.3`, `.4` and `.5`
  refuse the same documents for the same reason instead of each in its own idiom;
* the history walk picks revision 1, then revision 2, then refuses, at the three
  timestamps in `cases.json:history`;
* every row of `cases.json:normalisations` is what publish produces — which is why two
  authors who wrote the same rules in a different order publish byte-identical bytes,
  and why a re-publish that changed nothing cannot move a digest a verdict cited.

Two files live beside it, because a vector cannot exercise a store or a command line.
`crates/gitiup-quorum/tests/policy_store.rs` takes the same format into a real store:
publish it, read it back, resolve it with provenance, and refuse every store-shaped
failure (unsigned, not canonical, a blob the store cannot return, a signer the reader
does not trust, a lost update, a chain that runs backwards).
`crates/gitiup/tests/policy_cli.rs` runs `gitiup policy publish` and `gitiup policy
show` as command lines, because ADR-0004's `--dry-run`, exit-code and
provenance-printing clauses are only true of a binary.

If a vector and the Rust ever disagree, the vector is the rule: fix the Rust, and do not
edit `policies/*.json`, `cases.json` or `generate.py` to match a build.
